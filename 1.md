## 2026-09-17 — Phase 0 + Phase 1: concept grounding, data pipeline, MTBS validation

**What was built/learned:**
- Explained and applied spectral bands beyond RGB (NIR, SWIR), NBR
  (`(NIR-SWIR)/(NIR+SWIR)`), dNBR (before-NBR minus after-NBR) as the core
  change-detection signal for burn severity.
- Selected a real wildfire (Camp Fire, 2018) and validated it against the
  MTBS ground-truth database by querying MTBS's own ArcGIS REST data service
  directly (not just trusting search results) — confirmed exact Fire ID
  (`CA3982012144020181108`), acreage, and ignition date.
- Built a full Phase 1 data pipeline: NASA FIRMS API (fire detection
  cross-check), Google Earth Engine (Sentinel-2 imagery), and MTBS-on-GEE
  (ground truth severity raster) — three different geospatial data sources
  wired into one project.
- Hit and diagnosed a subtle geospatial bug: Sentinel-2's MGRS tile grid
  (`10TFK`) is larger than one satellite orbit pass's imaging swath, so two
  scenes tagged with the identical tile name can have completely different
  actual ground footprints depending on relative orbit (`R013` vs `R113`).
  A scene with perfect (0%) cloud-cover metadata turned out to have 0% real
  overlap with the area of interest. Fixed by explicitly computing
  footprint-vs-AOI intersection area for every candidate scene instead of
  trusting tile name + cloud percentage alone.
- Worked around Earth Engine's 48MB per-request direct-download cap by
  splitting a 6-band image into 6 single-band downloads.

**Interview questions this maps to:**
- "Walk me through how you'd detect wildfire burn severity from satellite
  imagery." → NBR/dNBR explanation, why NIR/SWIR bands specifically.
- "Tell me about a bug you found that wasn't obvious from the error message."
  → the tile/orbit footprint mismatch: a 400-error-free, 0%-cloud "success"
  that was silently wrong, caught by cross-checking actual geometry overlap
  rather than trusting metadata.
- "How do you validate that your data actually represents what you think it
  represents?" → FIRMS-vs-MTBS cross-validation, footprint-vs-AOI overlap
  checks, verifying file contents (pixel histograms) after every download
  instead of trusting exit codes/file existence alone.
- "How do you handle API limits/constraints in a data pipeline?" → FIRMS
  5-day max date range, Earth Engine 48MB download cap — both hit mid-session
  and worked around without changing the underlying data being pulled.
- "What's the difference between a satellite image's tile/scene ID and its
  actual coverage?" → MGRS tile grid vs. individual orbit swath footprints;
  same nominal tile, different real ground coverage.

## 2026-09-18 — Preprocessing, baseline diagnosis, and a U-Net that fixed a specific diagnosed weakness

**What was built/learned:**
- Full raster alignment pipeline: stacking single-band files into multi-band
  arrays, resampling a coarser categorical raster (MTBS, 30m) onto a finer
  grid (Sentinel-2, 10m) with nearest-neighbor (not bilinear/cubic, since
  averaging category codes produces meaningless values).
- Built a dNBR-threshold baseline using a data source's own per-instance
  calibrated thresholds (queried directly from MTBS's API) rather than
  generic textbook cutoffs — and was explicit that generic thresholds exist
  but the source's own values are more meaningful for direct comparison.
- Diagnosed a baseline's error pattern spatially (a confusion matrix alone
  hid it) — a disagreement map showed overestimation wasn't random noise but
  one solid, contiguous blob at the fire's core.
- Formed a specific, testable hypothesis for the bias (a missing calibration
  offset), tested it, and ruled it out cleanly (the correction moved overall
  agreement by 0.1 percentage points) — then documented the ruling-out itself
  as a learning, not just the confirmed things.
- Built a small U-Net from scratch (patch-based training, 12-channel input,
  region-based — not random-pixel — train/test split to avoid spatial-
  autocorrelation leakage) specifically targeting the diagnosed weakness, and
  confirmed via a second spatial comparison that it fixed that *specific*
  problem (the blob measurably broke up) rather than just improving
  aggregate numbers by chance.
- Hit and fixed a subtle NumPy bug: combining a `uint8` array with a negative
  Python int sentinel (`-100`) in `np.where` silently wrapped it to `156`
  (`-100 mod 256`) under NumPy's newer type-promotion rules, corrupting
  training labels with an out-of-range class index.

**Interview questions this maps to:**
- "How do you handle raster data at two different resolutions?" → nearest-
  neighbor vs. bilinear/cubic resampling, and why the choice depends on
  whether the data is categorical or continuous.
- "Walk me through how you'd validate a baseline model." → confusion matrix
  + overall accuracy is necessary but not sufficient; spatial visualization
  of errors caught a systematic bias that aggregate metrics alone hid.
- "Tell me about a hypothesis you tested that turned out to be wrong." →
  the dnbr_offst correction: a plausible, well-defined, specific hypothesis,
  cleanly tested and ruled out — a good example of honest negative results.
- "Why would a CNN/U-Net outperform a simple threshold rule for this kind of
  problem, specifically?" → a threshold rule is memoryless per-pixel by
  construction; a model with spatial context can treat a pixel differently
  based on its neighborhood, which directly explains why it fixed a spatially
  clustered error pattern a threshold rule structurally cannot fix.
- "How do you avoid data leakage when splitting a single image for
  train/test?" → region-based split instead of random-pixel split, and why
  random splitting of spatially autocorrelated data would let a model cheat.
- "Tell me about a subtle bug you've hit." → the uint8/-100 NumPy type-
  promotion wraparound — a bug where the code ran without error initially and
  produced a confusing downstream crash (or worse, could have silently
  corrupted training without crashing at all, if the wrapped value happened
  to fall in-range).

## 2026-09-19 — Phase 4/5 completion, and a full-stack web app (Phase 6, in progress)

**What was built/learned:**
- Shipped the final Phase 4 deliverable: a single composite image (before/
  after/severity + honest stat block) that explicitly scopes its validated
  accuracy figure to the held-out test region rather than implying the whole
  map was independently verified — a good example of writing metrics
  honestly even when it's less impressive-sounding.
- Hit two real bugs building that output: a figure-aspect-ratio mismatch
  that left dead white space (fixed by computing figure size from the actual
  cropped image aspect ratio rather than picking arbitrary dimensions), and
  a nodata-crop bug where a too-strict, single-stage threshold produced a
  zero-size array — root cause was that the nodata region was a contiguous
  horizontal band, not evenly spread across columns, so the fix needed a
  two-stage (rows-then-columns-within-those-rows) crop instead of one
  uniform threshold.
- Wrote a portfolio-quality README and a full end-to-end interview Q&A block
  covering the whole project's arc, including its own honest limitations
  section (single-fire generalization, a real precision trade-off, an
  untested remaining hypothesis) rather than only listing wins.
- Built a full-stack web app (Phase 6, in progress): FastAPI backend with a
  SQLite-backed API, and a Next.js + Leaflet frontend with a real interactive
  map (OpenStreetMap base layer + toggleable image-overlay layers positioned
  at the raster's true geographic bounds, converted from UTM to lat/lon).
- Hit a subtle SQL bug (INSERT placeholder count off by one vs. the table's
  column count) and fixed it by recounting both sides explicitly rather than
  guessing which one was wrong.
- Proactively caught a missing-CORS gap before the frontend needed it,
  rather than waiting for a confusing browser error to surface it later.
- Hit a real tooling limitation: no browser automation was available this
  session (declined by the user), so UI verification had to be handed off
  to the user's manual testing instead of self-verified — an honest example
  of knowing the limits of what could be confirmed independently.

**Interview questions this maps to:**
- "How do you decide what to show a non-technical stakeholder vs. a
  technical one?" → U-Net-primary/baseline-as-footnote decision for Phase 4,
  made explicitly to match the stated audience rather than showing everything.
- "Tell me about a bug that wasn't in the code you thought it was in." → the
  nodata-crop bug: the initial fix assumed a uniform 2D threshold would work,
  but the actual shape of the problem (a horizontal band) needed a
  fundamentally different, two-stage approach once actually measured instead
  of assumed.
- "How do you design an API before you know all the future requirements?" →
  the "preset list" architecture: built genuinely list-driven from day one
  even with only one real entry, specifically so adding more fires later is
  a data task, not a rewrite.
- "Tell me about a time you knew you couldn't fully verify your own work." →
  the browser-testing handoff: rather than claim the Leaflet map worked
  based on clean server logs alone, explicitly named what those logs could
  and couldn't prove, and asked the user to verify the part that mattered.

## Final Q&A — Wildfire BurnScan end to end

**"Walk me through this project."**
Given a NASA-confirmed wildfire (location + exact date), the goal is to
automatically map how severely different parts of it burned, using free
satellite imagery, and check the result against an official government
ground-truth dataset rather than just trusting it by eye. I picked the 2018
Camp Fire — confirmed present in the MTBS ground-truth database by querying
their data service directly rather than trusting search results — pulled a
before/after Sentinel-2 image pair, computed NBR (a standard vegetation/burn
index using near-infrared and shortwave-infrared bands), built a simple
threshold-based baseline severity classifier, diagnosed a specific weakness
in that baseline using a spatial error map (not just an accuracy number),
then built a small U-Net CNN specifically targeting that weakness and
confirmed it actually fixed it — not just improved some unrelated metric by
chance. Final output is a single map + stats package validated at 60.7%
agreement with MTBS, up from a 44.9% baseline.

**"Why this architecture — why a U-Net, and why not something else?"**
The threshold baseline is memoryless per-pixel by construction: the same
dNBR value always gets the same label, everywhere, with zero awareness of
neighboring pixels. A disagreement map showed the baseline's errors weren't
random — they were one solid, contiguous overestimation blob at the fire's
core (likely the flattened town of Paradise and totally consumed forest
around it). That's specifically a *spatial* failure mode, which a per-pixel
model (even a fancier one, like a Random Forest using more input features)
can't structurally fix — it still treats every pixel independently. A U-Net
looks at neighborhoods of pixels, so it can learn things like "a large,
texture-less patch of extreme signal often means completely bare/ashed
ground" — a distinction a global cutoff cannot represent. I kept it small (3
levels, from-scratch on one fire's patches) deliberately, rather than reaching
for a bigger pretrained architecture the dataset couldn't support.

**"How did you validate your results, and why should I trust the numbers?"**
Every claim in this project was checked, not assumed, including my own
work: the fire's presence in MTBS was confirmed via a direct API query
before locking it in, not trusted from search snippets. A "0% cloud cover"
scene turned out to have 0% actual overlap with the fire (different orbit
pass, same nominal tile) — caught by explicitly checking footprint geometry,
not just trusting metadata. The baseline was evaluated with a real confusion
matrix restricted to pixels valid in both datasets, not a rough visual
comparison. The U-Net's improvement was confirmed spatially, not just by a
single aggregate percentage — I specifically checked whether the diagnosed
core-overestimation problem shrank, not just whether some other number went
up. One explicit hypothesis (a missing MTBS calibration offset) was tested
and cleanly ruled out rather than left unexamined.

**"What are the limitations of this project? What would you change with more
time?"**
Three honest ones. First, single-fire dataset: the U-Net was trained and
evaluated on different regions of the *same* fire (a deliberate region-based,
not random-pixel, train/test split to avoid spatial-autocorrelation leakage)
— this proves the model beats the baseline on unseen regions of this fire,
not that it would generalize to a brand-new fire it's never seen. That would
need many more labeled fires. Second, the U-Net's improvement came with a
real trade-off: unburned-class precision dropped (70.3% → 48.9%) even as
moderate/high severity precision improved substantially — it's a net
positive, not a uniform win. Third, our before/after image pair (~3 months
apart) doesn't match MTBS's own reference pair (~1 year apart, different
sensor) — some of the remaining disagreement likely traces back to that
mismatch rather than model quality, and I didn't have time to test that
specific hypothesis the way I tested and ruled out the offset-correction one.
With more time: get a second labeled fire to test generalization, and try
matching MTBS's own before/after date spacing more closely.

**"What was the hardest part?"**
Not the modeling — it was catching problems that looked like successes. A
scene with perfect cloud-cover metadata that covered none of the actual fire
area. A `uint8`/negative-sentinel bug that silently wrapped -100 into 156
and crashed training several steps away from the actual bug. A baseline that
looked "okay" in aggregate (44.9%) but was hiding a specific, fixable,
spatially-concentrated bias that only showed up once I visualized errors
geographically instead of just computing a percentage.

**"Why does this matter / who would actually use this?"**
Burn severity mapping like this is used by land management agencies, fire
recovery planners, and insurance risk modeling — MTBS itself is a real
operational USGS/USFS product used for exactly this purpose. Automating a
faster, cheaper first-pass severity estimate (even at "beats a naive
baseline" quality, honestly reported) is directly useful for early damage
assessment before an official, slower analyst-reviewed map like MTBS's own
is available.
